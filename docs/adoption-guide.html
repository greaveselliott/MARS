Adoption

Adopt MARS without losing control.

MARS can act like a product engineering team, but adoption should start small: inspect first, write to a low-risk repo, review the generated harness, agree evidence, then increase autonomy only when the work earns trust.

Summary page: this guide helps choose a path. For canonical operating rules, use the documentation map. For security and regulated evaluation, start with security and governance.

Individual Developer

You want to see whether MARS helps without letting it loose on an important repo.

Concerns

  • What will it install locally?
  • What files can appear in my repo?
  • Can I inspect before agents run?
  • How do I remove it?

Safe first actions

  1. Run mars doctor --repo /path/to/repo --json.
  2. Run mars run engineer --repo /path/to/repo --dry-run --no-init.
  3. Use a disposable target for mars init.

Proof path

Review the diff after init, then read files and state, quickstart, and eject.

SME Tech Team

You want faster delivery without losing review, ownership, or release discipline.

Concerns

  • Who approves agent work?
  • How do tickets and plans stay readable?
  • Which checks count as evidence?
  • Can we pause the loop?

Safe first actions

  1. Choose one non-critical repo with real tests.
  2. Run mars init and review the harness diff as a team.
  3. Run one small role or lifecycle with a clear acceptance check.

Proof path

Inspect planning and delivery, checks evidence, observability, and release updates.

Enterprise Evaluator

You need governance, supportability, integration boundaries, and a practical rollout model.

Concerns

  • Where does data live?
  • What is optional versus default?
  • How do upgrades work?
  • How do we audit decisions?

Safe first actions

  1. Review the governance guide.
  2. Run an offline or local-only proof on a representative repo.
  3. Define approval gates before granting contributor or autonomous trust.

Proof path

Read configuration, integrations and validation, safety and quality, and DocSync.

Bank, Healthcare, Or Regulated Team

Start with control evidence. Do not start with a command catalog.

Concerns

  • Data locality and opt-in external surfaces.
  • Credential storage and redaction.
  • Human approval gates.
  • Rollback, eject, and incident review.

Safe first actions

  1. Confirm local-first assumptions and optional provider routes.
  2. Inspect generated target harness files in a sandbox repo.
  3. Agree allowed tools, roles, model routes, and acceptance evidence.

Proof path

Use the regulated proof path, credential docs, guardrails, and validation evidence.

Platform Or DevEx Owner

You are thinking about rollout, support, monitoring, upgrade cadence, and how MARS fits existing developer workflows.

Concerns

  • How many repos should be piloted first?
  • Who owns model, binary, and update policy?
  • How are failures surfaced?
  • How do teams standardize guardrails?

Safe first actions

  1. Create one pilot lane with explicit success and stop criteria.
  2. Run local checks, dashboard observation, and release/update smoke.
  3. Document org-specific guardrails and approval expectations.

Proof path

Read operations, dashboard API, models, release/update, and tools/MCP.

Maintainer Or Agent

You need the system records, not a simplified onboarding story.

Concerns

  • What is the active goal?
  • Which feature contract owns the behavior?
  • What ticket is the next slice?
  • Which docs must stay synced?

Safe first actions

  1. Read AGENTS.md and the foundation role packet.
  2. Open the active plan before creating tickets.
  3. Run DocSync and docs consistency checks after changes.

Proof path

Use canonical records, feature contracts, ticket lifecycle, and DocSync.

A Sensible Pilot Path

  1. Define the reason

    Pick one outcome: faster ticket delivery, better docs discipline, release support, local agent evaluation, or evidence capture.

  2. Pick a low-risk target

    Choose a repo with tests, clear owners, and work that matters but can be reverted.

  3. Inspect before writes

    Run doctor and dry-run role context before init or start.

  4. Review generated harness files

    Confirm roles, guardrails, tickets, BDD docs, release files, and ownership model are acceptable.

  5. Run one bounded slice

    Use one goal, one plan, one feature scenario, one ticket, and a small evidence gate.

  6. Decide trust level

    Increase autonomy only after the evidence is good enough for the team that owns the repo.
