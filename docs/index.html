Self-hosted autonomous delivery

Build, run, govern, and improve local AI engineering agents.

MARS installs a local-first agent operating system for a target repository: roles, guardrails, tools, tickets, BDD feature contracts, traces, scoring, trust, release discipline, and documentation sync. This site is the user-facing map for the system.

Start with the quickstart Open command reference

What MARS Is

The installed command

The mars binary prepares local inference, scaffolds target repos, runs agent roles, serves the dashboard, exposes tools through MCP, records telemetry, scores outcomes, and manages releases.

The deployed harness

A target repo receives .harness/, AGENTS.md, tickets, feature contracts, execution plans, release files, guardrails, skills, and knowledge routes. These files belong to that repo after initialization.

The target project

The application or library being built. MARS agents operate on target projects; the MARS source repo is the foundation system, not an ordinary target during autonomous runs.

The operating model

Durable goals, one active plan, BDD feature contracts, tickets, tests, traces, docs, release notes, scores, and trust changes are the source of truth. Chat is not the system of record.

Quickstart

The primary supported path today is a source checkout install, local setup, health check, and scoped run against a separate target repository. 

git clone https://github.com/greaveselliott/MARS.git
cd MARS
make install

mars setup --skip-github
mars doctor

mars start --repo /path/to/target-repo
Expected outcome: make install puts mars on your PATH, setup prepares local inference assets under ~/.mars/, doctor reports machine health, and start initializes, registers, and runs the target repo.

Inspect before running agents

Use dry-run mode to view assembled role context without calling a model.

mars init --repo /path/to/target-repo
mars run engineer --repo /path/to/target-repo --dry-run

Inspect a legacy repo safely

--no-init prevents automatic harness scaffolding during a dry run.

mars run engineer --repo /path/to/legacy-repo --dry-run --no-init

System Requirements

  • macOS or Linux, Git, and Go 1.22+ for source installs.
  • Network access for first setup downloads and optional release/auth operations.
  • Disk space for multi-GB GGUF model files under ~/.mars/models.
  • Recommended GPU: Apple Silicon/Metal, NVIDIA CUDA, or AMD ROCm.
  • CPU fallback is useful for development and dry runs, but normal autonomous operation expects GPU-backed local inference or an explicit cloud route.

Important Install Safety

Avoid go build ./cmd/mars; ./mars .... If the build fails, the semicolon can still run an old source-tree binary. Prefer make install for day-to-day use or go build -o build/mars ./cmd/mars for one-off binaries.

Planning And Delivery

MARS turns user intent into verifiable delivery through a strict chain: active goals, one active execution plan, BDD feature contracts, bounded tickets, evidence, review, and release notes. The chain keeps autonomous work from drifting into random backlog churn or unsupported completion claims.

Goal to plan

Goals define outcomes and tradeoffs. The active exec plan names which goal, BDD feature, scenario schedule, current failing scenario, and walking-skeleton slice is allowed to drive work.

BDD to ticket

Feature contracts define user-visible behavior step by step. Tickets implement only the current failing scenario or scenario group and carry scenario evidence before moving to done.

Evidence to release

Tests, commands, traces, quality score, validation reports, and docs checks prove the work. Release notes distinguish shipped scenarios from enabler work.

Target Harness Lifecycle

A target harness is the repository-local operating system MARS writes into a project. It is explicit, editable, versioned, and removable.

Initialize

Scaffold a new harness into a git checkout.

mars init --repo /path/to/repo

Creates .harness/, AGENTS.md, docs, tickets, feature contracts, release files, and starter role prompts.

Upgrade or update

Fill missing defaults without overwriting user-owned role prompts, manifests, guardrails, or docs.

mars update harness --repo /path/to/repo
mars upgrade --repo /path/to/repo

Eject

Preview and then remove generated harness files plus the associated per-repo database.

mars eject --repo /path/to/repo
mars eject --repo /path/to/repo --apply --confirm repo

eject does not rewrite git history. Use --keep-db to preserve the database.

Run Agents

One role, one target

Use run for manual work, dry-run inspection, role prompt debugging, or targeted repair.

mars run engineer --repo ~/my-project
mars run qa --repo ~/my-project --debug
mars run pipeline-fixer --repo ~/my-project --dry-run

Full scoped lifecycle

Use start when you want MARS to initialize, register, reconcile, and run one target repo.

mars start --repo ~/my-project
mars start --repo ~/my-project --model-endpoint http://127.0.0.1:8080/v1

Multi-repo daemon

Use register and serve when running a persistent orchestrator across registered repos.

mars register --repo ~/my-project --remote owner/repo
mars serve --addr :9091 --concurrency 2

Databases And Logs

  • start, register, and repo-scoped commands default to ~/.mars/db/{repo-name}/mars.db.
  • serve uses the shared legacy default ~/.mars/db/mars.db unless --db is supplied.
  • doctor --repo checks the per-repo database for that target.
  • run, start, and serve write verbose command logs under ~/.mars/traces/logs/ unless --log-file is supplied.

Models And Inference

MARS defaults to local open models served through llama.cpp as a subprocess. The Go binary remains CGO-free, model files live outside repos, and setup chooses a practical local bundle from detected hardware unless you explicitly configure cloud or deferred routing. For a full user reference, open the Models And Inference Guide.

Local bundles

mars models eligible --json
mars models list --eligible
mars setup --inference local --local-bundle auto

auto selects the highest-ranked bundle eligible for your hardware. Bundle names include local-cpu-q3, local-balanced-q4, and local-quality-q8.

Evaluate a candidate

mars models evaluate --provider ollama --model qwen3.6:27b
mars models evaluate --endpoint http://127.0.0.1:8080/v1 --model repo-coder

Evaluation reports capture reliability, latency, token counts, failures, and promotion status under docs/generated/model-evaluations/ by default.

Override routing

mars models override --repo ~/my-project --tier coding --provider ollama --model qwen3.6:27b
mars models override --repo ~/my-project --role engineer --provider openai-compatible --endpoint http://127.0.0.1:8088/v1 --model repo-coder

Overrides are written to .harness/model-overrides.yaml. Role overrides win before tier overrides.

Safety, Guardrails, Trust, And Tools

For the complete governance reference, open the Safety, Trust, And Quality Guide. It covers guardrail authoring, secret scanning, blast-radius containment, trust levels, scoring, quality score export, and telemetry.

Guardrails

YAML rules under .harness/guardrails/ can be hard-blocking or advisory. Hard rules are enforced during execution, not merely suggested in prompts.

mars guardrails secret-scan --repo ~/my-project
mars guardrails install-hooks --repo ~/my-project

Trust levels

observer reads and reports, contributor can perform human-triggered or ticket-bound mutation, and autonomous can self-schedule bounded work.

mars trust --repo ~/my-project
mars trust set engineer ~/my-project contributor --reason "Ticket-bound edits approved"

Built-in tools

Tools include file read/write, grep, shell exec, mars CLI, ticket creation, decision records, git operations, dependency sync, workspace hygiene, and meta tooling.

mars tools list --json
mars tools run git_status --repo ~/my-project --args-json '{}'

MCP surface

MCP-compatible clients can use the same tool registry without depending on a model provider.

mars mcp serve --repo ~/my-project --trust observer
mars mcp serve --repo ~/my-project --trust contributor --allowlist file_read,grep,mars_cli

Guardrail Rule Shape

rules:
  - id: no-hardcoded-secrets
    name: No hardcoded secrets
    severity: hard
    scope: global
    pattern: '(?i)(password|secret|api_key|token)\s*[:=]\s*["''][^"'']{8,}'
    message: Do not hardcode secrets. Use environment variables or a secrets manager.

Telemetry, Quality, And Learning

MARS uses local telemetry, scores, quality artifacts, and optional anonymous aggregate reporting to turn real outcomes into safer, better automation. Raw events stay local by default. The Safety, Trust, And Quality Guide documents score, trust, quality, and telemetry workflows in depth.

Quality score

mars scores --repo ~/my-project
mars scores export --repo ~/my-project --window-days 30

Refreshes docs/QUALITY_SCORE.md from live score, telemetry, ticket, dogfood, guardrail, check, no-op, and human follow-up evidence.

Anonymous telemetry

mars telemetry status --repo ~/my-project
mars telemetry preview --repo ~/my-project
mars telemetry export --repo ~/my-project --anonymous
mars telemetry send --repo ~/my-project

Preview shows the exact sanitized payload before export or send.

Foundation collector

mars telemetry collect --storage sqlite --addr :9092
mars telemetry triage-foundation --repo /path/to/MARS

Used by foundation maintainers to create source tickets from repeated anonymous foundation-owned patterns.

Release, Versioning, And Updates

MARS and initialized target repos use semantic versions and generated patch notes. Source releases also publish local binary assets and may mirror them to GitHub Releases. For the complete release lifecycle, open the Release And Update Guide.

Generate patch notes

mars release notes --repo . --bump auto --dry-run
mars release notes --repo . --bump auto
mars release backfill-notes --repo . --check

Updates VERSION, CHANGELOG.md, and in this repo internal/buildinfo/version.go.

Publish source assets

git tag -f vX.Y.Z
mars release publish-assets --repo . --version vX.Y.Z --upload auto
mars release verify-assets --dist dist/releases --version vX.Y.Z

The local dist gate is mandatory for source releases. GitHub mirroring is optional and separately verified when configured.

Update installed and deployed surfaces

mars update check --repo ~/my-project --json
mars update tool
mars update harness --repo ~/my-project

update check can recommend the tool update, the harness update, or both.

Customize And Extend MARS

For the user-facing tool bridge, MCP setup, trust levels, allowlists, and formal tool creation path, open the Tools And MCP Guide.

Edit roles

Change .harness/manifest.yaml and .harness/roles/*.md to add roles, remove roles, change tools, alter model tiers, or adjust triggers.

Add knowledge routes

Use .harness/knowledge/*.yaml to route compact context to docs such as architecture notes, API conventions, or domain glossaries.

Create reusable skills

Repeated, judgment-heavy human recovery steps should become scoped SKILL.md procedures rather than prompt bloat or chat memory.

Create tools deliberately

Repeated, risky, validation-heavy, or likely-to-recur deterministic procedures should become first-class tools through tool_create and tests.

name: my-project

Troubleshooting

SymptomCheckRecovery
mars is not found after install Open a new shell, run command -v mars, and inspect the install output. Run mars path setup with the installed binary or refresh shell command cache with hash -r.
Setup skips or fails model download Run mars doctor --json and check ~/.mars/models. Run mars setup --download or choose an eligible bundle with --local-bundle auto.
Local model is too slow or memory pressure is high Check hardware profile and model bundle with mars models eligible. Use performance_profile: balanced, reduce the local bundle, or use --model-endpoint for a real OpenAI-compatible endpoint.
Private release update returns auth errors Run mars auth github check. Authenticate with gh auth login, set GH_TOKEN or GITHUB_TOKEN, or run mars auth github setup.
A target repo has no harness but you only want inspection Use dry-run mode. mars run engineer --repo /path/to/repo --dry-run --no-init.
Dashboard port is occupied Check the command log for requested and actual listener addresses. Pass explicit --addr or --dashboard-addr, or free the port. Scoped start can fall back to an ephemeral local address.
Agent appears idle during generation Read the terminal dashboard phase and phase age. Slow local model calls can show waiting for model response; use debug logs to distinguish generation from a stuck tool.
Guardrail blocks a change Read the guardrail ID, scope, severity, and message. Change the implementation, narrow the rule, or use an audited override only when policy allows it.
Release notes are missing narrative sections Run mars release backfill-notes --repo . --check. Run mars release backfill-notes --repo . and include compliant changelog updates in the release-note commit.
Tool or harness appears stale Run mars update check --repo /path/to/repo --json. Run the recommended mars update tool, mars update harness, or both.
